# План интеграций (после локальной беты)

Статус: **черновик, ждёт решений I1–I5**. Ничего из этого не реализуется до выбора команды.

## Что уже готово в коде

| Часть | Где | Что умеет |
|---|---|---|
| Контракт хранилища | `src/storage/gateway.ts` | документы с ревизиями, транзакции, конфликт `StorageConflictError` |
| Локальная реализация | `src/adapters/idbStorageGateway.ts` | тот же контракт на IndexedDB — сейчас в продукте |
| Слияние правок | `src/storage/fieldMerge.ts` | сохраняет только изменённые поля, сливает непересекающиеся правки, показывает конфликт по одному полю |
| Модель внешних систем | `src/model/external.ts` | подключения, паспорта возможностей, проекции сущностей, конфликты, очередь публикации |
| Пакетный менеджер | `src/local/publishing.ts` | очередь → проверка → подтверждение → отправка → повтор (сейчас на тестовых назначениях) |

Интеграция сводится к двум адаптерам: **серверный `StorageGateway`** (общие кампании для со-мастеров) и **настоящий `ExternalGateway`** (lovegame / lorebook / systemsetup вместо тестовых).

## Открытые решения

| # | Вопрос | Варианты |
|---|---|---|
| I1 | Где хранить общие кампании | **A** Cloudflare Worker + D1 (приложение уже деплоится на Cloudflare) · **B** Firestore (контракт изначально задуман «в форме Firestore») · **C** приватный GitHub-репозиторий через Contents API (как в старой архитектуре) · **D** не синхронизировать, только экспорт/импорт |
| I2 | Как мастер входит в систему | **A** Cloudflare Access (вход по почте) · **B** Firebase Auth (Google) · **C** GitHub OAuth · **D** без входа, общий ключ кампании |
| I3 | Что такое внешние системы и как с ними говорить | **A** читать JSON с их сайтов (GitHub Pages), публиковать через PR в их репозитории · **B** только чтение, без публикации · **C** у систем есть свой API — нужен его адрес и формат |
| I4 | Правило конфликтов при совместной правке | **A** пополевое слияние и ручной выбор при конфликте (готово в `fieldMerge`) · **B** «последняя запись побеждает» · **C** правит только ответственный мастер, остальные читают |
| I5 | Порядок | **A** сначала синхронизация со-мастеров, потом внешние системы · **B** сначала внешние системы (публикация), синхронизация позже |

## Этапы после выбора

| Этап | Содержание | Зависит от |
|---|---|---|
| И-0 | Спецификация API/схемы выбранного хранилища, секреты в настройках окружения, тестовый стенд | I1, I2 |
| И-1 | Серверный `StorageGateway` + вход; локальный IndexedDB остаётся кэшем и работает офлайн | I1, I2 |
| И-2 | Совместная правка: ревизии, слияние, экран конфликтов, права владельца/со-мастера на сервере | И-1, I4 |
| И-3 | Настоящий `ExternalGateway`: подключения, паспорта возможностей, чтение проекций | I3 |
| И-4 | Публикация через пакетный менеджер в реальные назначения, журнал отправок | И-3 |

## Что нужно от команды, кроме выбора

- Адреса и формат данных внешних систем (lovegame, lorebook, systemsetup).
- Кто может создавать ключи и секреты в выбранном хранилище (они не коммитятся в репозиторий).
- Сколько мастеров и кампаний ожидается — от этого зависят лимиты бесплатных тарифов.
