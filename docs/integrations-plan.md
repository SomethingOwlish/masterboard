## Серверная часть Masterboard (И-1, сервер) — готово

- `wrangler.jsonc` + `worker/src/index.ts`: один Worker отдаёт SPA и API `/api/*`.
- D1 (`worker/migrations/0001_documents.sql`): документы кампаний с ревизиями, таблица участников для доступа.
- Вход: подпись JWT Cloudflare Access проверяется по ключам команды (`worker/src/auth.ts`); для локальной разработки — `DEV_USER_EMAIL`.
- API: `GET /api/me`, `GET /api/collections/localCampaigns`, `GET|PUT|DELETE /api/docs/localCampaigns/<id>`; `PUT` с `expectedRevision` возвращает 409 и текущий документ при конфликте.
- Права D2 на сервере (`worker/src/permissions.ts`): состав мастеров, архив и удаление — владелец; запуск, закрытие, разбор и передачу сессии — ответственный мастер или владелец. Мастер определяется по почте из входа.
- Что нужно сделать в Cloudflare один раз (не в репозитории): `wrangler d1 create masterboard` → id в `wrangler.jsonc`; `npm run worker:migrate`; приложение Access на домен Masterboard → `ACCESS_TEAM_DOMAIN`, `ACCESS_AUD`.

## Общие кампании в интерфейсе (И-1 клиент, И-2 слияние) — готово

- **Весь Мастерборд за входом (решение F1).** При запуске приложение спрашивает `GET /api/me`. Есть почта (вход через Cloudflare Access) — работает серверный каталог (`src/local/remote.ts`). Нет — показывается только экран входа (`SignInPage`); в продакшене его заслоняет страница Access с кодом на почту. Режима «только в браузере» больше нет.
- Новые кампании и импорт сразу создаются на сервере, владелец — вошедший мастер.
- Кампании, оставшиеся в IndexedDB с прежних времён, видны плашкой «В этом браузере N кампаний» с кнопкой «Перенести все»: кампании уезжают на сервер, вошедший мастер становится владельцем, копии в браузере удаляются. Пример «Лунный порт» в пустой браузер больше не кладётся.
- Разработка: `npm run worker:dev` (Worker на :8787, вход подставляется из `DEV_USER_EMAIL`) + `npm run dev` (Vite проксирует `/api`).
- У мастера есть поле `email`. В общей кампании владелец добавляет со-мастера только с почтой; мастер «вы» определяется по входу, переключателя нет.
- Запись идёт с ожидаемой ревизией. При `409` правка трёхсторонне сливается с версией сервера (`src/local/merge.ts`): разные поля и разные элементы списков (по `id`) объединяются автоматически; если оба мастера изменили одно и то же, остаётся версия сервера, а на экране — сообщение «Правки объединены» с перечнем мест.
- **Живое обновление (27.09.2026).** Открытая общая кампания раз в 10 секунд спрашивает только номер ревизии (`GET /api/revisions/localCampaigns/<id>`) — пока вкладка видна и нет неотправленных правок. Номер вырос — документ забирается и показывается; при возврате на вкладку спрашивает сразу. Неотправленные правки опрос не трогает: их сольёт следующая запись.
- **Окно «моя / их» (27.09.2026).** Места, которые оба мастера поменяли одновременно, копятся на плашке «Правки объединены · Вы и мастер Лис изменили одно и то же — N мест» с кнопкой «Разобрать». В окне по каждому месту («Библиотека › Смотритель › мотив») две версии; по умолчанию остаётся чужая, «моя» записывается новой ревизией. Снимок сервера теперь несёт `updatedBy` — почту того, чья версия осталась.
- **Без сети — исключено (27.09.2026).** Правка при обрыве связи не теряется (черновик в браузере, отправка при связи или по «Синхронизировать»), но открыть Мастерборд без сети нельзя: запуск упирается во вход через Access. Service worker не делаем.

## Лорбук, ЛавГеймс и SystemSetup (И-3, И-4) — готово

Путь: браузер → `/api/ext/*` на Worker Мастерборда → service binding `LOREBRIDGE` → `/mb/*` в lorebridge (контракт `docs/contracts/lorebridge-masterboard.md`; маршруты — lorebridge#76, статус «в архиве» — lorebook#130).

- **Дверь** (`worker/src/bridge.ts`): Worker добавляет общий секрет и почту вошедшего мастера, ответ моста (включая `409` с `current`) отдаёт как есть. Нет привязки или секрета — `501 {kind:'unconfigured'}`, и экраны так и пишут.
- **Связи кампании (F4)**: в «Публикации» владелец выбирает мир Лорбука и кампанию ЛавГеймс (`campaign.integrations`); остальные мастера видят выбор. SystemSetup — только чтение.
- **Импорт (F2)**: «Библиотека → Из источника» — записи связанного мира/кампании и систем SystemSetup, отмечаете нужные, «Добавить N в библиотеку». Каждая сущность помнит источник (`entity.sources`: система, мир, id, тип, ссылка, время изменения там и согласованный снимок). Поля, для которых у типа нет места, хранятся под своей подписью и уезжают обратно без изменений.
- **Обновить из источника (I4)**: трёхстороннее сравнение со снимком: изменённое только там — берётся, только здесь — остаётся, с обеих сторон — окно «Изменено с обеих сторон» с выбором по каждому полю. Запись заархивирована там — сущность уходит в архив.
- **Публикация (F3)**: тип там предлагается по таблице (`TARGET_TYPE` в `src/local/integration.ts`) из того, что принимает паспорт, и меняется в очереди. Уже опубликованная сущность обновляется, а не создаётся заново; перед отправкой к операции добавляются id записи и время, когда мы её видели, — чужая правка даёт `409` и подсказку «обновите из источника». После успеха сущность запоминает запись там; в истории — ссылка «открыть».

### Что нужно сделать на Cloudflare (однократно, не из репозитория)

Подробная пошаговая инструкция — [`docs/deploy-cloudflare.md`](deploy-cloudflare.md).

1. Оба Worker (`masterboard`, `lorebridge`) — в одном аккаунте; в `wrangler.jsonc` Мастерборда уже есть `services: LOREBRIDGE → lorebridge`.
2. Один и тот же секрет в обоих: `wrangler secret put MASTERBOARD_BRIDGE_SECRET` (в каталоге Мастерборда и в каталоге lorebridge).
3. Задеплоить lorebridge (с маршрутами `/mb/*`), затем Мастерборд.

## Что уже готово в коде

| Часть | Где | Что умеет |
|---|---|---|
| Контракт хранилища | `src/storage/gateway.ts` | документы с ревизиями, транзакции, конфликт `StorageConflictError` |
| Локальная реализация | `src/adapters/idbStorageGateway.ts` | тот же контракт на IndexedDB — сейчас в продукте |
| Слияние правок | `src/storage/fieldMerge.ts` | сохраняет только изменённые поля, сливает непересекающиеся правки, показывает конфликт по одному полю |
| Модель внешних систем | `src/model/external.ts` | подключения, паспорта возможностей, проекции сущностей, конфликты, очередь публикации |
| Пакетный менеджер | `src/local/publishing.ts` | очередь → проверка → подтверждение → отправка → повтор (сейчас на тестовых назначениях) |

Интеграция сводится к двум адаптерам: **серверный `StorageGateway`** (общие кампании для со-мастеров) и **настоящий `ExternalGateway`** (lovegame / lorebook / systemsetup вместо тестовых).
