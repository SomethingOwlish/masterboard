Статус: **решения приняты 26.09.2026**, идёт этап И-0.

| # | Решение |
|---|---|
| I1 | **A** — Cloudflare Worker + D1. Сравнение бесплатных тарифов с Firebase: для нашего масштаба бесплатны оба; выбран Cloudflare — один поставщик с хостингом и бесплатный вход по почте до 50 человек |

## Серверная часть Masterboard (И-1, сервер) — готово

- `wrangler.jsonc` + `worker/src/index.ts`: один Worker отдаёт SPA и API `/api/*`.
- D1 (`worker/migrations/0001_documents.sql`): документы кампаний с ревизиями, таблица участников для доступа.
- Вход: подпись JWT Cloudflare Access проверяется по ключам команды (`worker/src/auth.ts`); для локальной разработки — `DEV_USER_EMAIL`.
- API: `GET /api/me`, `GET /api/collections/localCampaigns`, `GET|PUT|DELETE /api/docs/localCampaigns/<id>`; `PUT` с `expectedRevision` возвращает 409 и текущий документ при конфликте.
- Права D2 на сервере (`worker/src/permissions.ts`): состав мастеров, архив и удаление — владелец; запуск, закрытие, разбор и передачу сессии — ответственный мастер или владелец. Мастер определяется по почте из входа.
- Что нужно сделать в Cloudflare один раз (не в репозитории): `wrangler d1 create masterboard` → id в `wrangler.jsonc`; `npm run worker:migrate`; приложение Access на домен Masterboard → `ACCESS_TEAM_DOMAIN`, `ACCESS_AUD`.
- Дальше (И-1, клиент): у мастера появляется поле «почта», клиентский `HttpStorageGateway`, режим «общая кампания», перенос локальной кампании на сервер.

## Аудит соседних систем (26.09.2026)

| Система | Что это | Данные | API сегодня |
|---|---|---|---|
| lovegame | платформа кампаний для мастера и игрока | Firestore `lovegame-3c83d` | своего нет; только через lorebridge, и не для персонажей/NPC/раздаток |
| lorebook | миры и лор, два автора | Firestore `lorebook-4338a` | своего нет; lorebridge умеет создавать сущности, скрывать, менять статус — но только в контексте кампании lovegame |
| systemsetup | конструктор игровых систем, паки для lovegame | Firestore (свой проект) | своего нет; lorebridge отдаёт опубликованные паки на чтение |
| lorebridge | Cloudflare Worker — единственная дверь между системами | ключи сервисных аккаунтов, D1, KV, R2 | принимает только Firebase ID-токены; нет списков с `updatedAt`, обновления, архива, паспорта возможностей |

Вывод: внешние интеграции Masterboard строятся **через lorebridge**. Недостающие маршруты добавляются туда; в lorebook, возможно, понадобится состояние «в архиве». Конкретный план — после решений E1–E4 (см. ниже в чате/артефакте).

## Что уже готово в коде

| Часть | Где | Что умеет |
|---|---|---|
| Контракт хранилища | `src/storage/gateway.ts` | документы с ревизиями, транзакции, конфликт `StorageConflictError` |
| Локальная реализация | `src/adapters/idbStorageGateway.ts` | тот же контракт на IndexedDB — сейчас в продукте |
| Слияние правок | `src/storage/fieldMerge.ts` | сохраняет только изменённые поля, сливает непересекающиеся правки, показывает конфликт по одному полю |
| Модель внешних систем | `src/model/external.ts` | подключения, паспорта возможностей, проекции сущностей, конфликты, очередь публикации |
| Пакетный менеджер | `src/local/publishing.ts` | очередь → проверка → подтверждение → отправка → повтор (сейчас на тестовых назначениях) |

Интеграция сводится к двум адаптерам: **серверный `StorageGateway`** (общие кампании для со-мастеров) и **настоящий `ExternalGateway`** (lovegame / lorebook / systemsetup вместо тестовых).

## Варианты, из которых выбирали

| # | Вопрос | Варианты |
|---|---|---|
| I1 | Где хранить общие кампании | **A** Cloudflare Worker + D1 (приложение уже деплоится на Cloudflare) · **B** Firestore (контракт изначально задуман «в форме Firestore») · **C** приватный GitHub-репозиторий через Contents API (как в старой архитектуре) · **D** не синхронизировать, только экспорт/импорт |
| I2 | Как мастер входит в систему | **A** Cloudflare Access (вход по почте) · **B** Firebase Auth (Google) · **C** GitHub OAuth · **D** без входа, общий ключ кампании |
| I3 | Что такое внешние системы и как с ними говорить | **A** читать JSON с их сайтов (GitHub Pages), публиковать через PR в их репозитории · **B** только чтение, без публикации · **C** у систем есть свой API — нужен его адрес и формат |
| I4 | Правило конфликтов при совместной правке | **A** пополевое слияние и ручной выбор при конфликте (готово в `fieldMerge`) · **B** «последняя запись побеждает» · **C** правит только ответственный мастер, остальные читают |
| I5 | Порядок | **A** сначала синхронизация со-мастеров, потом внешние системы · **B** сначала внешние системы (публикация), синхронизация позже |

## Что нужно от команды, кроме выбора

- Адреса и формат данных внешних систем (lovegame, lorebook, systemsetup).
- Кто может создавать ключи и секреты в выбранном хранилище (они не коммитятся в репозиторий).
- Сколько мастеров и кампаний ожидается — от этого зависят лимиты бесплатных тарифов.
